# 대회·내전 관전 및 방송 파이프라인

이 문서는 대회·내전 경기에서 **선수 PC의 데이터, 관전 클라이언트, 자동 관전 카메라, OBS, YouTube, 웹 관전 페이지**를 하나의 방송 흐름으로 연결하는 목표 구조를 기록한다. 현재 저장소에는 이 파이프라인의 구현이 없으며, 관전 클라이언트의 `activePlayer: null` 사례 이외의 데이터 반환 범위와 실시간 카메라 제어 수단은 실전 검증이 필요하다.

## 현재 운영 방향

**관전 PC의 로컬 API와 화면 인식을 먼저 사용하고, 부족한 필드에 한해 선수 PC 수집기를 추가하는 혼합 방식**을 우선 검토한다. 아래 전체 흐름의 선수 PC 수집 경로는 목표 구조이며, 실제 설치 대수는 방송에 필요한 필드를 시험한 뒤 결정한다. 영상과 오버레이를 같은 게임 시간으로 맞추고 **합성 후 약 30초 송출 지연**을 초기 운영안으로 검토한다. 30초는 확정 설정이나 실측 지연값이 아니다.

| 방식 | 이점 | 제약 |
| --- | --- | --- |
| 선수 PC별 로컬 수집기 | 화면에 표시되지 않는 해당 선수의 로컬 API 값까지 구조화해 수집 가능 | 최대 10대 설치·인증·업데이트·연결 감시가 필요하고, 선수 데이터가 관전 영상보다 앞설 수 있음 |
| 관전 PC 화면 인식 | 한 PC에서 운영하며 관전 영상과 같은 시점의 HUD 값을 읽기 쉬움 | 화면에 보이지 않는 값은 얻을 수 없고, HUD·해상도·패치 변화와 화면 가림에 따라 인식률이 달라짐 |
| 혼합 방식 | 관전 API·화면 인식으로 얻는 값을 우선 쓰고 필요한 선수별 상세값만 추가 수집 | 필드별 출처·신뢰도와 게임 시간 동기화 규칙이 필요함 |

관전 응답의 `activePlayer`가 `null`인 사례가 있으므로 이를 선수 상세값 공급원으로 쓰지 않는다. 관전 응답의 `allPlayers`·`events`·`gameData` 범위와 화면 인식 정확도를 먼저 확인한다. `activePlayer.currentGold`는 현재 보유 골드이며 선수별 누적 골드가 아니므로, 선수 PC에 수집기를 둔다고 해서 라인별 누적 골드 차이를 바로 계산할 수 있는 것은 아니다.

## 전체 흐름

```text
필요한 선수 PC의 LoL 클라이언트
    → PC별 로컬 수집기(필드 검증 후 배치)
    → 웹 서버: 인증·수신·저장·경기/선수 매핑
    → 송출 PC: 경기 데이터 수신 ──────────────┐
                                             ↓
관전 클라이언트 → 관전 PC의 로컬 수집기·화면 인식 → 시점 비교·검증 → 방송 상태 → OBS 오버레이
       │                                      │
       ├→ 관전 화면 → 영상 캡처 ───────────────┴───────────────→ OBS → 송출 지연(초기안: 30초) → YouTube 라이브
       │                                                          → 웹 관전 페이지의 플레이어
       └← 자동 관전 제어기 ← 이벤트·화면 인식·카메라 판단
                           ↖ 운영자 수동 제어
```

기본 배치는 **관전 클라이언트와 OBS를 송출 PC에서 실행**하는 것이다. 장비를 분리하면 관전 PC가 영상과 관전 데이터를 송출 PC로 전달하고, 나머지 처리 순서는 같다. 웹 서버는 배치한 선수 PC 수집기의 원본 데이터를 중앙에 모으고 송출 PC에 전달한다. 관전 클라이언트 영상은 게임 화면의 기준 시점이다.

## 단계별 역할

| 단계 | 입력과 처리 | 출력 |
| --- | --- | --- |
| 선수 PC 수집 | 각 PC의 로컬 게임 데이터 API에서 사용 가능한 플레이어·이벤트 값을 지속적으로 읽는다. | 출처 PC, 경기·세트 ID, 선수 ID, 게임 시간, 수집 시각을 붙인 샘플 |
| 웹 서버 | 수집기 인증, 경기·선수 매핑, 중복 제거, 최근 상태 저장, 연결 상태 감시를 수행한다. | 송출 PC에 전달할 선수별 데이터와 이벤트 |
| 송출 PC 수신 | 서버의 상태 변경을 받고 재연결 시 현재 스냅샷을 다시 가져온다. | 비교 대기 중인 선수 데이터 |
| 관전 데이터 수집·비교 | 관전 클라이언트에서 실제 제공되는 값과 게임 시간을 읽어 선수 데이터의 같은 **게임 시점**과 대조한다. | 방송용으로 채택된 값, 불일치·누락 상태 |
| 관전 화면 자동화 | 이벤트·영상 인식 결과를 이용해 보여줄 위치와 대상 선수를 판단한다. 검증된 조작 수단으로 카메라를 움직이고 운영자가 언제든 개입한다. | 관전 클라이언트 영상 |
| 합성·송출 | OBS가 관전 영상을 캡처하고 검증된 데이터를 오버레이로 합성한다. | YouTube 라이브 영상; 웹 관전 페이지에 삽입 |

**데이터 비교는 단순히 같은 순간에 도착한 값을 맞대는 작업이 아니다.** 관전 화면은 선수 PC보다 늦을 수 있으므로 서버 수신 시각뿐 아니라 경기 ID·세트 ID·게임 시간을 기준으로 같은 시점의 샘플을 찾는다. 허용 오차와 필드별 우선순위는 실제 관전 테스트 후 결정한다. 관전 값이 없는 필드는 선수 PC 값과 화면 인식 결과를 대조하고, 확인되지 않은 값은 방송에 확정값처럼 표시하지 않는다. 데이터가 끊기면 마지막 검증값의 시각을 표시하거나 해당 오버레이를 숨기고 운영자가 수정할 수 있게 한다.

관전 클라이언트의 `gamedata.json` 형태 응답에서 `activePlayer`가 `null`인 사례가 확인되었다. 따라서 관전 PC의 `activePlayer`에서 보유 골드·상세 능력치 등을 읽는 경로는 방송 필드의 출처로 잡지 않는다. 관전 PC의 `allPlayers`·`events`·`gameData` 반환 범위는 별도 검증하고, 선수별 상세값은 선수 PC 수집 또는 검증된 다른 출처로 확보한다.

## 자동 관전 카메라

카메라 자동화는 **관측 → 관심 장면 판단 → 카메라 명령 → 화면 결과 확인** 순서로 설계한다. 이벤트 데이터는 교전·처치·오브젝트 같은 후보 장면을 찾는 데 쓰고, 화면 인식은 실제 관전 화면에서 챔피언 위치와 장면 전환 결과를 확인하는 데 쓴다. 경기 이벤트만으로 화면의 모든 상황을 알 수 없으므로 초기 운영에는 수동 카메라 제어와 자동 제어 중지 기능을 둔다.

[Riot Replay API와 League Director](SPECTATOR_AUTOMATION_RESEARCH.md#관전-카메라-직접-제어-자료)는 **리플레이 카메라 제어**를 문서화한다. 현재 자료만으로는 진행 중인 경기의 관전 카메라를 같은 방식으로 제어할 수 있다고 확정할 수 없다. 실전 관전에서 가능한 조작 경로와 화면 인식 정확도를 별도 시험한 뒤 자동 제어 방식을 정한다. 검증 전에는 AI가 카메라를 직접 제어하는 것을 완료된 기능으로 취급하지 않는다.

## 지연 예산: 실제 게임에서 시청자 화면까지

아래 수치는 **설계용 추정치**다. Riot과 YouTube가 공개한 설정값 외의 구간은 이 프로젝트에서 측정한 값이 아니다. 실제 지연은 지역, 관전 방식, 네트워크, 수집 주기, 카메라 처리, OBS 설정, YouTube 플레이어 상태에 따라 달라진다.

| 구간 | 지연의 원인 | 설계용 추정 또는 공식 안내 |
| --- | --- | --- |
| 실제 게임 → 관전 클라이언트 | LoL 관전 지연 설정, 관전 데이터 버퍼 | [Riot 패치 14.1](https://www.leagueoflegends.com/en-sg/news/game-updates/patch-14-1-notes/)의 소환사의 협곡 일반 관전은 **2분 30초**. [패치 25.17](https://www.leagueoflegends.com/en-sg/news/game-updates/patch-25-17-notes/)부터 커스텀 게임의 **로비 관전자**는 지연 제거 옵션이 있다. 지연 제거 시에도 실제 화면·네트워크 지연은 0이 아니므로 테스트 전에는 약 **0.5~3초**를 가설로 둔다. |
| 선수 PC → 서버 → 송출 PC | 로컬 API 폴링, 전송, 서버 처리, 구독 | 같은 지역의 안정적인 회선과 짧은 폴링 간격을 가정한 **약 0.1~1초 목표치**. 측정값이 아니다. |
| 관전 값 비교·AI 카메라·오버레이 → OBS | 관전 게임 시간에 맞춘 샘플 선택, 화면 분석, 카메라 조작, 렌더링 | 처리 목표 **약 0.2~2초**. AI가 다음 장면을 늦게 선택하면 그만큼 추가된다. |
| OBS → YouTube 시청자 | 인코딩·전송·트랜스코딩·플레이어 버퍼 | [YouTube 공식 도움말](https://support.google.com/youtube/answer/7444635?hl=en)의 일반적인 시청자 기준: **초저지연은 5초 미만, 저지연은 10초 미만**. 이는 고정값이나 모든 시청자의 보장치는 아니다. 일반 지연 모드에는 고정 초 단위 안내가 없다. |

**무지연 옵션을 켠 커스텀 경기:** 관전 클라이언트 화면은 실제 경기보다 대략 **1~5초**, YouTube 시청 화면은 송출 지연을 추가하지 않았을 때 대략 **3~12초** 늦는 것을 초기 계획 범위로 둔다. 이는 공식 SLA가 아니라 위 처리 구간을 보수적으로 더한 추정이다. **합성 후 30초 송출 지연을 적용하면 시청 화면의 계획 범위는 대략 33~42초**가 되며, 실제 값은 측정해야 한다. 버퍼링이 생기면 더 길어진다.

**관전 지연이 켜진 경기:** 기본 소환사의 협곡 일반 관전과 같은 **2분 30초 지연이 적용된다고 가정할 때**, 관전 화면은 약 **2분 30초+처리 지연**, YouTube 시청 화면은 송출 지연을 추가하지 않았을 때 대략 **2분 33초~2분 42초** 늦을 수 있다. 별도의 30초 송출 지연을 걸면 그만큼 더해진다. 커스텀 경기의 실제 지연값은 해당 로비 설정과 클라이언트에서 확인해야 한다. [패치 25.17](https://www.leagueoflegends.com/en-sg/news/game-updates/patch-25-17-notes/)에 따르면 무지연 옵션을 켜면 친구 목록에서 관전하는 기능은 사용할 수 없으며, 이 옵션은 로비 관전자에게 적용된다.

**30초 지연의 위치:** 초기안은 관전 영상과 같은 게임 시간의 오버레이를 먼저 합성한 뒤 OBS의 송출 지연을 적용하는 것이다. [OBS는 Stream Delay 기능을 제공한다](https://obsproject.com/kb/obs-studio-overview). 이 방식은 이미 합성된 과거 화면을 30초 동안 수정하는 기능을 주지 않는다. 운영자가 지연 구간 안에서 값을 정정하려면 관전 영상과 시간별 데이터를 **합성 전**에 버퍼링하는 별도 구성이 필요하다. 어느 경우든 30초 지연만으로 영상·선수 데이터가 자동 정렬되지는 않는다.

선수 PC 데이터가 관전 화면보다 먼저 도착해도 **그 차이를 전부 방송 지연에 추가할 필요는 없다.** 서버가 게임 시간별 샘플을 보관하고 송출 PC가 관전 화면의 게임 시간에 해당하는 과거 샘플을 선택하면 된다. 예를 들어 관전 화면이 150초 늦었다면 송출 PC는 선수 PC의 최신값이 아니라 약 150초 전 경기 상태를 오버레이에 쓴다. 카메라 판단과 웹페이지의 별도 통계도 같은 관전 시점에 맞춰야 경기 결과가 영상보다 먼저 드러나지 않는다.

실측은 같은 처치·오브젝트 이벤트의 **선수 화면 시각, 관전 화면 시각, 서버 수신 시각, OBS 출력 시각, YouTube 플레이어 시각**을 각각 기록해 비교한다. 같은 벽시계 시각과 게임 시간을 함께 저장하고 최소 여러 번 반복해 중앙값과 느린 구간을 확인한다.

## 영상과 웹 시청

OBS는 관전 클라이언트의 영상과 방송 상태 오버레이를 **같은 송출 단계에서** 합성한 뒤 YouTube로 보낸다. 웹 관전 페이지는 YouTube 라이브 플레이어를 보여 주므로 시청자마다 LoL 관전 클라이언트를 설치할 필요가 없다. 웹페이지에 별도의 실시간 선수 통계를 표시한다면 YouTube 영상보다 앞서 결과가 노출되지 않도록 영상의 게임 시간에 맞춰 지연 표시한다.

밴픽은 경기 화면과 다른 수집 경로가 필요할 수 있다. [서비스 계획](SERVICE_PLAN.md)의 밴픽 모듈과 운영자 수동 입력 경로를 사용한다. 선수 PC의 로컬 API에 없는 값, 관전 클라이언트에서 반환하지 않는 값, 화면 인식이 불확실한 값은 출처와 확신도를 구분해 다룬다.

## 구현·검증 순서

1. 실제 커스텀 경기에서 **관전 PC의 로컬 API·화면 인식 결과와 시험용 선수 PC 수집값**을 동시에 기록해 방송 필드별 출처를 정한다. 필요가 확인된 선수에게만 수집기를 배치한다.
2. 경기·세트·선수 식별자와 게임 시간으로 샘플을 연결하고 관전 지연 및 불일치율을 측정한다.
3. 송출 PC에서 검증된 상태를 OBS 오버레이에 표시하고 관전 화면과 일치하는지 확인한다.
4. 합성 후 30초 송출 지연을 시험하고 YouTube 및 웹 관전 페이지에서 영상·오버레이·별도 웹 통계의 시간 차를 측정한다. 운영 중 정정 시간이 필요한지도 확인한다.
5. 녹화된 관전 화면에서 관심 장면 탐지와 카메라 판단을 먼저 평가한다. 실제 관전 클라이언트의 조작 수단을 검증한 후 자동 제어를 연결한다.
