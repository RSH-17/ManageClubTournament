# 대회·내전 통합 웹 서비스 구상

## 목표와 현재 상태

하나의 웹 서비스에서 대회와 내전을 모두 운영한다. 참가자는 경매, 일정·공지, 대진표, 문의, 관전 화면을 이용하고 운영자는 경기 진행과 방송 화면을 관리한다. 이 문서는 **경매를 선수 영입 경매로 가정**한다. 입찰 규칙과 참가 조건은 실제 운영 방식이 정해지면 조정한다.

현재 저장소에는 [Next.js 프론트엔드](../apps/web/)와 [NestJS 백엔드](../apps/api/)의 기본 환경이 있으며, 서비스 기능은 아직 구현 중이다. [chat.md](chat.md)는 이전 방송 UI 구상, [RIOT_APIS.md](RIOT_APIS.md)는 Riot API 조사, [JSON_FIELDS.md](JSON_FIELDS.md)는 로컬 JSON 샘플 분석이다. [lol_live_data.py](../apps/collector/lol_live_data.py)와 [sample_data](../sample_data/)에 로컬 데이터 수집 스크립트와 밴픽·인게임 JSON 샘플이 있다. 이 자료를 프로토타입의 출발점으로 사용한다.

## 공통 운영 모델

대회와 내전을 별개 서비스로 만들지 않고 하나의 **이벤트(Event)** 로 관리한다. 이벤트에는 종류(대회/내전), 이름, 설명, 운영자, 참가 조건, 공개 여부, 상태, 일정과 기능 설정을 둔다. 경매·대진표·방송 기능은 이벤트별로 켜고 끈다. 내전은 간단한 팀 편성과 단일 경기만 사용할 수 있고, 대회는 여러 라운드와 세트 점수를 사용할 수 있다.

| 객체 | 역할 |
| --- | --- |
| User, EventMember | 계정과 이벤트별 역할. 운영자·팀장·참가자·시청자를 구분한다. |
| Team, Player, Roster | 팀, 선수, 소속과 경기별 출전 명단을 관리한다. |
| Auction, Lot, Bid | 경매 설정, 대상 선수, 입찰 기록과 낙찰 결과를 관리한다. |
| Match, Game | 대진 한 경기와 그 안의 세트를 분리해 결과·일정·방송 상태를 연결한다. |
| Announcement, ScheduleEntry | 공지와 경기 일정을 관리하고 변경 이력을 남긴다. |
| Inquiry, InquiryReply | 문의·답변·처리 상태를 관리한다. |
| GameSnapshot, GameEvent | 수집된 인게임 상태와 이벤트를 실제 경기·세트에 연결한다. |

처음에는 단일 서버와 관계형 데이터베이스로 시작한다. 경매 입찰과 낙찰 확정은 서버의 데이터베이스 트랜잭션에서 처리한다. WebSocket은 상태 변경을 즉시 전달하고, 연결이 끊긴 사용자는 일반 API로 현재 상태를 다시 받아야 한다.

## 화면과 권한

| 화면 | 참가자·시청자 기능 | 운영자 기능 |
| --- | --- | --- |
| 이벤트 홈 | 소개, 참가 정보, 다음 경기, 주요 공지 확인 | 이벤트 설정과 공개 상태 관리 |
| 경매 | 선수·예산·입찰 현황 확인, 권한 있는 팀장의 입찰 | 선수 등록, 시작·마감, 낙찰 확정·취소 |
| 일정·공지 | 일정표, 공지, 변경 내역 확인 | 일정 편집, 공지 게시 |
| 대진표 | 라운드, 경기 상태, 세트 점수, 다음 경기 확인 | 결과 입력·승인, 대진 진행 |
| 문의 | 문의 작성, 본인 문의와 답변 확인 | 답변, 처리 상태 관리 |
| 관전 | 방송 영상과 경기 정보 확인 | 연결 상태 점검, 방송 화면 전환·수동 수정 |
| OBS 화면 | 방송 장비에서 투명 배경 오버레이 사용 | 밴픽·점수판·선수 HUD·이벤트 표시 제어 |

문의 내용은 작성자와 운영자만 읽도록 한다. 운영자 조작과 결과 정정은 기록을 남긴다. OBS 화면도 공개 참가자 화면과 권한을 구분한다.

경매 전에 시작 예산, 최소 입찰 단위, 마감 직전 입찰 시 연장 여부, 동시 입찰 우선순위, 팀당 선수 수, 취소·재경매 규칙을 확정한다. 서버 시각으로 마감을 판정하고 예산 초과·중복 낙찰을 막는다. 클라이언트 화면에 보이는 남은 시간은 안내용이다.

대진표의 Match는 한 대진을, Game은 세트를 뜻한다. 예를 들어 3판 2선승은 하나의 Match와 최대 세 개의 Game으로 표현한다. 결과를 운영자가 승인하면 다음 라운드를 갱신한다. 지연·재경기·기권·결과 정정을 처리할 수 있도록 수동 수정 경로를 둔다.

## 관전과 방송 데이터

**YouTube 방송에도 게임 데이터 수집이 필수 요구사항이다.** 목표 구조와 단계별 역할은 [관전 및 방송 파이프라인](BROADCAST_PIPELINE.md)에 정리했다. 관전 자동화에 관한 공식 문서와 공개 구현은 [관전 자동화 자료 조사](SPECTATOR_AUTOMATION_RESEARCH.md)에 정리했다.

초기 운영안은 **관전 PC의 로컬 API·화면 인식을 우선 사용하고, 꼭 필요한 선수별 상세값에 한해 선수 PC 수집기를 배치**하는 혼합 방식이다. 관전 클라이언트의 `gamedata.json` 형태 응답에서 `activePlayer`가 `null`인 사례가 확인되어, 관전 PC의 활성 플레이어 상세값에 의존할 수 없다. 송출 PC는 관전 화면과 선수 PC 데이터를 **동일 경기 시점**으로 맞춰 방송 상태를 만든다. AI·화면 인식 기반 제어기는 관전 화면 자동 운영의 검증 대상이며, OBS가 영상과 데이터 오버레이를 합성해 YouTube로 송출한다. 합성 후 **약 30초 송출 지연**을 초기안으로 시험하고, 웹사이트는 YouTube 플레이어로 방송을 제공한다. 실제 관전 클라이언트의 나머지 데이터 범위, 화면 인식 정확도, 라이브 카메라 제어 방식은 구현 전 검증한다. 세부 비교와 지연 처리 방법은 [방송 파이프라인](BROADCAST_PIPELINE.md#현재-운영-방향)에 정리했다.

Riot Live Client Data API는 게임이 실행되는 PC의 로컬 주소에서 읽는다. 현재 스크립트는 로컬 JSON 저장까지만 한다. 선수 PC 수집기가 필요해지면 서버 전송, 수집 PC 인증, 재접속, 샘플 시각과 경기 ID 연결, 끊김 감지와 운영자 수동 보정이 필요하다. [JSON 필드 분석](JSON_FIELDS.md)에서 활성 플레이어와 참가자 목록의 필드 차이를 확인할 수 있다. [Riot Live Client Data API](https://developer.riotgames.com/docs/lol#live-client-data-api)

밴픽 수집은 League Client API를 사용하는 별도 모듈로 취급한다. Riot은 이 API를 제3자 앱용 공식 지원 대상으로 보장하지 않는다. 따라서 밴픽 화면과 경기 상태 처리는 수동 입력만으로도 동작하도록 만들고 자동 수집은 검증 후 연결한다. [Riot League Client API](https://developer.riotgames.com/docs/lol#league-client-api)

Tournament API는 선택 연동이다. 사용 가능하면 대회 코드, 로비 운영, 경기 종료 후 결과 콜백에 연결할 수 있다. **실시간 선수별 경기 상태 공급원으로 설계하지 않는다.** 사용할 수 없는 이벤트는 운영자가 결과를 입력·승인한다. [Riot Tournament API](https://developer.riotgames.com/docs/lol#tournament-api)

## 권장 구현 구조

| 폴더 | 내용 |
| --- | --- |
| web/ | 참가자·시청자·운영자 화면과 OBS 오버레이 |
| server/ | 인증·권한, 이벤트, 경매, 일정, 대진표, 문의, 실시간 전송 |
| collector/ | 로컬 LoL 데이터 수집과 서버 전송 |
| docs/ | 설계와 데이터 설명 |

초기 기술 구성은 React 웹 화면, Node.js 서버, PostgreSQL 데이터베이스를 권장한다. WebSocket으로 경매·경기 상태 변경을 전파한다. 실제 접속자 수와 운영 부담이 확인된 뒤 서비스를 분리한다. 공개 화면에 필요한 값만 서버에서 내보내고, 밴픽 JSON의 채팅 JWT·비밀번호와 Riot API 키는 전송·로그·브라우저 응답에서 제외한다.

## 개발 순서

1. **기초 운영:** 계정·이벤트별 권한, 이벤트 생성, 팀·선수 등록.
2. **운영 웹:** 공지, 일정, 문의, 대진표, 결과 입력·승인.
3. **경매:** 예산·입찰·낙찰 규칙과 실시간 현황, 운영자 조정 기록.
4. **방송 데이터 검증:** 실제 관전 PC에서 밴픽·인게임 필드를 기록하고 방송 화면에 필요한 값의 출처를 확정한다.
5. **수집·경기 상태 처리:** 필드별 출처를 확정하고 필요한 PC에 수집기를 배치한다. 서버 전송, 선수·팀 매핑, 이벤트 중복 제거, 끊김 표시, 운영자 수동 보정을 구현한다.
6. **방송 화면:** 수집 데이터로 갱신되는 OBS 오버레이, 약 30초 송출 지연 시험, YouTube 송출, 웹사이트의 YouTube 관전 페이지.
7. **선택적 Riot 연동:** 접근 권한이 갖춰진 API만 추가하고 종료 후 결과와 내부 대진표를 연결.

첫 운영 검증은 **이벤트 하나에서 참가자 등록부터 경매, 일정·대진 진행, 데이터 수집을 포함한 YouTube 방송, 결과 발표까지 완주하는 것**이다. 방송용 데이터 수집은 출시 후 선택 기능으로 미루지 않는다.

공개 서비스에 Riot 웹 API를 사용하려면 제품 등록과 적절한 API 키가 필요하다. 개발 키는 공개 서비스용이 아니며 Tournament API 접근은 별도 승인 대상이다. [Riot Developer Portal 키 안내](https://developer.riotgames.com/docs/portal#api-keys)
